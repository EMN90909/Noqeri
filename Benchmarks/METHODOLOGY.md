# Noqeri benchmark methodology

Performance is evidence, not branding. Noqeri must not say it is faster than Rust, Zig, C, C++, Go, or another implementation unless a reproducible result bundle supports the exact claim.

## Native-execution qualification

Runtime comparisons for Noqeri must time a standalone `native-aot` executable. The executable must be produced from `noqeri build` output and linked with the minimal ABI host in `Runtime/native/aot_runner.cpp`. The benchmark harness rejects `noqeri run`, `noqeri-nqri`, and `.nqri` artifacts for Noqeri runtime measurements.

The current qualified AOT helper, `scripts/native-build.mjs`, is deliberately limited to Linux x86-64 because the current C++ native backend emits the SysV x86-64 calling convention. Extending the target matrix requires target-correct machine-code lowering and an equivalent qualification test first.

A native program benchmark is not automatically a self-hosting benchmark. Current provenance records `self_hosted_compiler: false` because the AOT path is generated by the Stage-0 C++ compiler. Until the Noqeri-written compiler itself emits and runs native Stage-2/Stage-3 executables without `noqeri-nqri`, performance reports must keep those facts separate.

## Required workloads

The tracked suite is `Benchmarks/suite.json`: binary trees, JSON, regex, HTTP server, filesystem, database, matrix operations, allocation, strings, sorting, startup, and compilation. Every comparative implementation must perform equivalent work and validate an equivalent result before its timing is accepted.

## Comparison languages

Published comparative runs target Noqeri, C, C++, Rust, Zig, and Go. Versions, optimization flags, link mode, allocator changes, feature flags, execution model, and runtime settings are part of the result, not footnotes that may be omitted.

## Run protocol

1. Record git revision, Noqeri compiler revision, peer compiler versions, OS/kernel, CPU model/count, memory, power mode, and relevant environment variables.
2. Build release artifacts before timing runtime workloads. Compilation is measured separately.
3. For Noqeri runtime workloads, retain the generated `.native.json` provenance and verify the timed executable SHA-256 matches it.
4. Every runtime command must declare deterministic `expected_stdout`. The harness runs one untimed validation execution and rejects the workload before warm-ups if the output differs.
5. Perform at least three warm-ups, then at least fifteen timed samples unless a workload documents why that is impractical.
6. Report the raw sample list plus median and p95. Record peak RSS and binary size where meaningful.
7. Pin server/client topology and concurrency for network tests. Do not compare a loopback single-request microbenchmark to a production server configuration.
8. Do not discard inconvenient samples without recording the exclusion and reason.
9. Keep historical result bundles. A graph without the underlying JSON/CSV evidence is not release evidence.

## Regression gates

Important workloads fail validation when their median exceeds the accepted baseline by more than the workload's `threshold_percent`. The baseline must have been captured on the same benchmark host/profile. Cross-machine results are informative, not gating.

Run `node scripts/perf-gate.mjs baseline.json candidate.json` to enforce the policy. The gate intentionally has no fabricated baseline in the repository; the first baseline must come from a measured, archived run.

## Claims

Allowed: "On host X, revision A measured Y ms median for workload Z; revision B measured W ms using the published methodology."

Allowed when the evidence says so: "The Noqeri program was compiled to a native Linux x86-64 executable by the Stage-0 compiler and measured against C under the recorded flags."

Not allowed without matching evidence: "Noqeri is 1.1x C", "Noqeri is faster than Rust/Zig/C++", or broad claims extrapolated from a VM/interpreter run, one microbenchmark, or a result bundle that hides the compiler/execution model.
