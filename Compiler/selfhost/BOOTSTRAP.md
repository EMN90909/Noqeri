# Noqeri bootstrap ownership

Noqeri compiler semantics live in `Compiler/selfhost/*.noqeri`: lexical analysis, parsing, semantic analysis, generic inference, NIR lowering, optimization, safety checks, target policy and NQRI serialization are Noqeri-owned.

## Pinned NQRI bootstrap acceptance chain

The current self-host bootstrap is an **NQRI bytecode bootstrap**. It is not a native-code self-host proof. `scripts/build.sh` and `scripts/build.ps1` delegate to `scripts/bootstrap-nqri.*` and enforce one concrete acceptance chain:

1. Build or locate `noqeri-nqri`, the C++ NQRI virtual machine in `Runtime/native/nqri_vm.cpp`.
2. Load the committed Stage-1 compiler from `Compiler/selfhost/trusted-stage1.nqri` and its digest from `Compiler/selfhost/trusted-stage1.sha256`.
3. Require that digest to match the canonical identity in `Compiler/selfhost/stage1-seed.sha256`, then SHA-256 the committed binary itself. Stage 1 is never executed unless all identities agree.
4. Require the verified Stage-1 seed to export `stage2CompileToNqri`.
5. Execute Stage 1 in `noqeri-nqri` to build `noqeri-stage2.nqri` from `Compiler/selfhost/stage2-sources.txt`.
6. Execute Stage 2 against the exact same source closure to build `noqeri-stage3.nqri`.
7. Reject the bootstrap unless Stage 2 and Stage 3 are byte-for-byte identical.
8. In CI, rebuild Stage 1 with GCC-built and Clang-built Stage-0 compilers and require both outputs to be byte-for-byte identical to the committed Stage-1 file.

The compiler export `stage2CompileToNqri` owns parse -> semantic analysis -> NIR lowering -> optimization -> validation -> NQRI serialization. The C++ VM decodes and executes the stable NQRI instruction format. It does not implement the compiler frontend.

The proof generated by this path is intentionally explicit:

```text
execution_model=nqri-vm
artifact_format=nqri
native_codegen=false
native_selfhost=false
```

A process being a native C++ executable does not make the code it interprets native machine code. NQRI bootstrap evidence must never be used as evidence for a native runtime performance claim.

## Native self-host status

True native self-hosting is **not qualified yet**. The Noqeri-written `backend.noqeri` currently validates NIR and target/ABI contracts, while the Noqeri ELF/COFF/Mach-O writers currently provide format/header primitives rather than a complete machine-code, symbol and relocation emission pipeline.

For that reason, `scripts/bootstrap-native.sh` and `scripts/bootstrap-native.ps1` fail closed instead of aliasing the NQRI VM path. They may only become successful native proof entry points after the Noqeri-written compiler can emit an executable Stage-2 compiler, run it without `noqeri-nqri`, rebuild Stage 3 natively, and pass the native equivalence/conformance gates.

The Stage-0 C++ backend can already emit Linux x86-64 assembly for supported programs. `scripts/native-build.mjs` uses that path to create standalone native executables for runtime benchmarking, but its provenance records `self_hosted_compiler: false`. That solves execution-model honesty for benchmarks; it does not claim the compiler itself is self-hosted natively.

## Canonical Stage-1 pin

The canonical Stage-1 pin currently identifies:

```text
sha256 c4c6108d627653931494e40d40697c7a0ff79f0fb62d856e4dabe92b69cbb0e8
bytes  4452905
```

That exact seed was reproduced by both GCC-built and Clang-built Stage-0 compilers in GitHub Actions run `39585410281`. In the same accepted run, Stage 2 and Stage 3 were byte-identical and both hashed to `7fed1cfc89ae551c3c2eaa5b3309311ddbfe7a075d890e7df5ef06c9e7a0a409`.

### Windows

```powershell
.\bootstrap.ps1

# Optional externally audited Stage-1 NQRI seed:
$env:NOQERI_STAGE1_NQRI = "C:\path\to\audited-stage1.nqri"
$env:NOQERI_STAGE1_SHA256 = "YOUR_AUDITED_64_DIGIT_SHA256"
.\bootstrap.ps1
```

The default path writes `build/nqri-selfhost-proof.json` only after pin verification and Stage-2/Stage-3 byte equality.

### Linux and macOS

```sh
./bootstrap.sh

NOQERI_STAGE1_NQRI=/path/to/audited-stage1.nqri \
NOQERI_STAGE1_SHA256=YOUR_AUDITED_SHA256 \
./bootstrap.sh
```

A prebuilt NQRI VM can be supplied with `NOQERI_NQRI_RUNTIME`. `NOQERI_TARGET` can override automatic target selection. Stage-0 is not required for the default NQRI bootstrap; CI rebuilds it to prove the committed seed remains reproducible.

## What the pin proves

The repository has a canonical Stage-1 identity. A locally produced Stage-1 NQRI artifact is rejected unless it exactly reproduces the bytes identified by the committed SHA-256 pin. CI additionally requires GCC and Clang Stage-0 builds to reproduce that same pin.

This is stronger than accepting an arbitrary freshly generated Stage-1 candidate, but it is not independent external attestation. `stage1_independently_trusted=false` remains explicit in proof records. It is also not native-code self-host evidence.

## Verification policy

NQRI self-host evidence is accepted only when:

- the committed Stage-1 NQRI bytes match both pin files before execution;
- `tests/bootstrap_seed_pin.test.mjs` passes;
- independent GCC and Clang Stage-0 builds reproduce the Stage-1 bytes;
- Stage 1 builds Stage 2 from the checked source closure;
- Stage 2 rebuilds Stage 3 from that exact source closure;
- Stage 2 and Stage 3 NQRI files are byte-for-byte identical;
- the NQRI VM self-test passes;
- required compiler/runtime conformance suites pass.

`Runtime/nqri-vm.mjs` remains a reference/parity implementation and is not the default bootstrap executor. `scripts/bootstrap-stage2.mjs` remains useful for broader release-suite orchestration.

Cross-language interoperability is a separate contract using the versioned embedding C ABI and adapters documented in `Doc/ABI.md` and `Doc/FFI.md`.
